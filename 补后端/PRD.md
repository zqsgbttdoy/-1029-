# 监理现场管理系统 — 产品需求文档（PRD）

---

## Problem Statement

建筑工程监理行业长期依赖纸质文档和手工流程管理现场工作，导致监理日记/日志/安全日志等核心文档的填写、审核、归档效率低下，容易出现遗漏和延误。监理人员需要在多个项目间切换，缺乏统一的工作平台来管理巡检记录、通知单、联系单、会议纪要等业务文档。项目资料散落在各处，无法按工程目录结构系统化归档。管理层难以实时掌握各项目监理工作进展和人员履职情况。现有流程中，审核环节依赖线下传递，回复跟踪困难，逾期无法自动提醒，严重影响监理工作质量和合规性。

---

## Solution

构建一套**监理现场管理系统**，以 Web 应用形式为监理团队提供统一的工作平台。系统涵盖监理现场工作的全流程：从日常巡检、旁站监督，到监理日记/日志/安全日志的填写与审核，再到监理通知单/工作联系单的下发与回复跟踪，以及会议纪要、月报的编制归档。系统支持工程资料按目录结构上传归档，提供数据统计与报表功能辅助管理决策，并通过角色权限体系和工作标准配置确保流程合规。

---

## User Stories

### 一、仪表盘与概览

1. 作为监理人员，我希望登录后看到仪表盘概览，以便快速了解当前项目整体状况和待办事项
2. 作为监理人员，我希望在仪表盘看到项目总数、进行中、已完成、待审核的统计卡片，以便掌握项目整体进度
3. 作为监理人员，我希望在仪表盘看到待办事项列表，以便及时处理待审核和待回复的工作
4. 作为监理人员，我希望在仪表盘有快捷入口跳转到各业务模块，以便快速进入常用功能
5. 作为总监理工程师，我希望在仪表盘看到各项目异常数据汇总，以便及时发现和处置问题

### 二、项目台账管理

6. 作为监理人员，我希望查看所有监理项目的列表，以便了解项目基本信息和状态
7. 作为监理人员，我希望新建项目并填写项目编号、名称、建设单位、总监理师、起止日期等信息，以便录入新项目
8. 作为监理人员，我希望编辑项目信息，以便更新项目变更内容
9. 作为监理人员，我希望按状态（筹备中/进行中/已暂停/已完成）筛选项目，以便快速定位目标项目
10. 作为监理人员，我希望搜索项目，以便按名称或编号快速查找
11. 作为监理人员，我希望删除项目，以便清理无效数据

### 三、日常巡检

12. 作为监理人员，我希望新建日常巡检记录，填写巡检日期、巡检人、巡检内容等信息，以便记录每日巡检情况
13. 作为监理人员，我希望在巡检记录中添加发现的问题，并标记问题状态（未修改/已修改），以便跟踪问题整改进度
14. 作为监理人员，我希望上传巡检照片，以便留存现场影像证据
15. 作为监理人员，我希望按项目、状态、日期筛选巡检记录，以便快速查找历史记录
16. 作为监理人员，我希望删除草稿状态的巡检记录，以便清理误建的数据
17. 作为监理人员，我希望导出巡检数据，以便生成报告或存档

### 四、旁站检查

18. 作为监理人员，我希望新建旁站检查记录，填写旁站部位、工序、起止时间、管理人数、施工人数等信息，以便记录关键工序的旁站监督情况
19. 作为监理人员，我希望选择旁站工序类型（混凝土浇筑/防水施工/钢筋隐蔽/土方回填/桩基施工），以便规范化记录
20. 作为监理人员，我希望在旁站记录中关联所属工程资料目录，以便将旁站记录归入对应分部分项
21. 作为监理人员，我希望在旁站记录中添加发现的问题并跟踪修改状态，以便确保问题闭环
22. 作为监理人员，我希望选择旁站结果（完成/交班），以便记录旁站结束方式
23. 作为监理人员，我希望按项目、状态、工序、日期筛选旁站记录，以便快速定位

### 五、监理通知单

24. 作为监理人员，我希望新建监理通知单，填写编号、项目、签发人、下发日期、回复截止、接收单位、通知内容、整改要求，以便向施工单位下发整改通知
25. 作为监理人员，我希望在通知单中关联巡检记录，以便追溯通知来源
26. 作为监理人员，我希望通知单支持完整生命周期（草稿→已下发→已回复→已验证），以便跟踪通知单处理全流程
27. 作为监理人员，我希望在通知单下发后，施工单位能进行回复，以便记录整改情况
28. 作为监理人员，我希望对已回复的通知单进行验证（上传照片和附件），以便确认整改结果
29. 作为监理人员，我希望通知单逾期时自动标记，以便催办逾期未回复的通知
30. 作为监理人员，我希望编辑草稿状态的通知单，以便修改后再下发
31. 作为监理人员，我希望删除草稿状态的通知单，以便清理误建数据

### 六、工作联系单

32. 作为监理人员，我希望新建工作联系单，填写编号、项目、发送方、接收单位、联系内容，以便与参建单位进行工作沟通
33. 作为监理人员，我希望联系单支持完整生命周期（草稿→已发送→已回复→已验证），以便跟踪联系单处理全流程
34. 作为监理人员，我希望在联系单中上传照片和附件，以便补充说明联系事项
35. 作为监理人员，我希望对已回复的联系单进行验证，以便确认处理结果
36. 作为监理人员，我希望联系单逾期时自动标记，以便及时跟进

### 七、监理日记

37. 作为监理人员，我希望新建监理日记，填写日期、天气、风力、气温、施工情况、管理情况、巡检情况、晨会情况、图纸审查、其他事项，以便记录每日监理工作
38. 作为监理人员，我希望上传日记照片和附件，以便留存现场资料
39. 作为监理人员，我希望提交日记后进入审核流程（草稿→待审核→审核通过/驳回），以便确保日记质量
40. 作为审核人，我希望审核监理日记，可以批准或驳回（附驳回原因），以便把控日记质量
41. 作为监理人员，我希望驳回后的日记可以修改后重新提交，以便修正问题
42. 作为监理人员，我希望查看日记的版本历史，以便追溯修改记录
43. 作为监理人员，我希望在发起人/审核人角色间切换，以便在同一界面完成不同角色的操作
44. 作为监理人员，我希望按项目、状态、日期筛选日记，以便快速查找
45. 作为监理人员，我希望导出日记数据，以便生成报告

### 八、监理日志

46. 作为监理人员，我希望新建监理日志，填写日期、天气、施工内容、管理情况、巡检情况等信息，以便汇总周报形式的监理工作
47. 作为监理人员，我希望点击"从监理日记获取"按钮，系统自动从已审批的监理日记中提取当日数据填充到日志表单，以便减少重复录入
48. 作为监理人员，我希望"从监理日记获取"功能按作者分组展示内容，并在多作者时标注作者姓名，以便区分不同人员的工作记录
49. 作为监理人员，我希望"从监理日记获取"功能仅提取当日（单一日期）的日记数据，不跨日期汇总，以便保持日期与工作内容的一一对应
50. 作为监理人员，我希望"从监理日记获取"功能仅填充当前为空的字段，以便保留已手动填写的内容
51. 作为监理人员，我希望在日志中选择所属工程资料目录，以便将日志归入对应分部分项
52. 作为监理人员，我希望日志支持审核流程和版本历史，以便确保日志质量和可追溯
53. 作为监理人员，我希望查看日志的版本历史，以便追溯修改记录

### 九、安全日志

54. 作为监理人员，我希望新建安全日志，填写天气、施工情况、安全检查情况、安全生产状况、重大事项，以便记录每日安全巡查情况
55. 作为监理人员，我希望上传安全日志照片和附件，以便留存安全检查影像
56. 作为监理人员，我希望安全日志支持审核流程和版本历史，以便确保记录质量
57. 作为审核人，我希望审核安全日志，可以批准或驳回，以便把控安全记录质量

### 十、会议纪要

58. 作为监理人员，我希望新建会议纪要，填写会议主题、类别（例会/专题会/安全会/其他）、时间、地点、记录人、内容、决议，以便记录会议成果
59. 作为监理人员，我希望在会议纪要中上传附件，并为每个附件选择所属工程资料目录，以便系统化归档
60. 作为监理人员，我希望按项目、状态筛选会议纪要，以便快速查找

### 十一、监理月报

61. 作为监理人员，我希望新建监理月报，填写报告期次、报告类型（综合月报/安全月报/质量月报）、编制人、工作概述、存在问题及建议，以便定期汇总监理工作
62. 作为监理人员，我希望在月报中上传附件并关联工程资料目录，以便归档
63. 作为监理人员，我希望按项目、状态筛选月报，以便快速查找

### 十二、工程资料目录与上传

64. 作为监理人员，我希望配置工程资料目录结构（单位工程→分部工程→分项工程），以便建立标准化的资料分类体系
65. 作为监理人员，我希望通过右键菜单新增、重命名、排序、删除目录节点，以便灵活维护目录结构
66. 作为监理人员，我希望按项目上传工程资料文件到对应目录，以便系统化归档项目文档
67. 作为监理人员，我希望支持拖拽上传文件，以便提高上传效率
68. 作为监理人员，我希望查看已上传文件列表，以便确认资料上传情况
69. 作为监理人员，我希望删除已上传文件，以便清理错误上传的资料

70. 作为总监理工程师，我希望查看监理日记提交统计（提交率、缺失统计），以便监督人员履职情况
71. 作为总监理工程师，我希望查看监理日志提交和审核统计，以便了解日志编制质量
72. 作为总监理工程师，我希望查看安全日志提交和审核统计，以便掌握安全检查执行情况

80. 作为监理人员，我希望一键标记所有消息已读，以便快速处理积压消息
81. 作为监理人员，我希望一键清空所有消息，以便重置消息列表

## Implementation Decisions

### 技术架构

- **后端**: Spring Boot 3.2.5 + Java 17 + Spring Data JPA + Hibernate 6 + MySQL 8.0，采用经典三层架构（Controller → Service → Repository）
- **前端**: 纯 HTML/CSS/JS，无前端框架，24 个独立 HTML 页面，所有样式和脚本内联
- **数据库连接池**: Alibaba Druid
- **API 风格**: RESTful，统一响应格式 `ApiResponse<T>`（code/message/data），分页格式 `PageResult<T>`（list/total/pageNum/pageSize）
- **部署架构**: Nginx 反向代理 + Spring Boot 内嵌 Tomcat，前端静态文件由 Nginx 托管，API 请求代理至后端

### 数据模型

- **系统模块（8 张表）**: 用户、部门、角色、权限、角色权限关联、用户角色关联、操作日志、消息、工作标准配置
- **业务模块（8 张表）**: 项目、日常巡检、旁站检查、监理通知、工作联系单、监理日记、监理日志、安全日志、会议纪要、监理月报、子项数据库、项目文档
- **树形结构**: 部门（parent_id 自关联）、权限（parent_id 自关联）、子项数据库（parent_id 自关联）均通过自关联实现
- **多对多关系**: 用户↔角色（sys_user_role 中间表）、角色↔权限（sys_role_permission 中间表）
- **照片/附件**: 以 JSON 字符串存储在 TEXT 类型字段中
- **消息多态关联**: Message 通过 related_id + related_type 关联任意业务实体

### 状态流转

- **监理日记/日志/安全日志**: 草稿(draft) → 待审核(pending) → 审核通过(approved) / 驳回(rejected)，驳回后可修改重新提交产生新版本
- **监理通知单**: 草稿(draft) → 已下发(issued) → 已回复(replied) → 已验证(verified) / 已逾期(overdue)
- **工作联系单**: 草稿(draft) → 已发送(sent) → 已回复(replied) → 已验证(verified) / 已逾期(overdue)
- **日常巡检/旁站检查**: 草稿(draft) → 已记录(recorded)，无需审核
- **会议纪要/月报**: 草稿(draft) → 已提交(submitted)
- **软删除**: 绝大多数实体删除为软删除（status 设为 inactive），查询默认排除

### 核心业务逻辑

- **"从监理日记获取"功能**: 调用 `/api/supervision-diaries?status=approved` 获取已审批日记，按当日（单一日期）过滤，解析作者姓名（通过 `/api/users/{id}`），按作者分组聚合填充到日志表单，仅填充空字段
- **审核流程**: 通过 ApproveDTO 传递审核操作（通过/驳回+原因），Service 层更新状态并记录审核人、审核时间
- **回复机制**: 监理通知单和工作联系单通过 ReplyDTO 接收回复内容，自动设置回复日期
- **版本管理**: 监理日记/日志/安全日志支持 newVersion() 方法，基于现有记录创建新版本（version+1）
- **仪表盘统计**: DashboardController 聚合待处理通知、待处理联系单、异常日记/日志/安全日志数、未读消息数
- **旁站起止时间精度**: 电脑端与小程序均采用“日期 + 整点 + 分钟（5 分钟一档）”点选，写回 `YYYY-MM-DD HH:mm:00`；接口接收与返回 ISO 格式 `YYYY-MM-DDTHH:mm:ss`，服务端原样保存分钟，不做取整。历史记录中的非档位时间（如 `08:15:30`）打开面板时原样回显，未重新选择就确定不会覆盖原值。结束时间必须晚于开始时间：前端未确认不写值，服务端 `!end.isAfter(start)` 返回 400“旁站结束时间必须晚于开始时间”

### API 端点（约 80 个）

- **认证**: POST /auth/login, POST /auth/logout, GET /auth/info
- **用户管理**: CRUD + 状态更新（6 个端点）
- **部门管理**: CRUD（5 个端点）
- **角色管理**: CRUD + 权限分配 + 用户分配（7 个端点）
- **权限管理**: CRUD + 树形结构（6 个端点）
- **项目管理**: CRUD + 状态更新（6 个端点）
- **日常巡检**: CRUD（5 个端点）
- **旁站检查**: CRUD（5 个端点）
- **监理通知单**: CRUD + 回复（6 个端点）
- **工作联系单**: CRUD + 回复（6 个端点）
- **监理日记**: CRUD + 审核（6 个端点）
- **监理日志**: CRUD + 审核（6 个端点）
- **安全日志**: CRUD + 审核（6 个端点）
- **会议纪要**: CRUD（5 个端点）
- **监理月报**: CRUD（5 个端点）
- **子项数据库**: CRUD + 树形结构（6 个端点）
- **项目文档**: CRUD + 上传（6 个端点）
- **消息**: CRUD + 标记已读 + 未读数（6 个端点）
- **操作日志**: 分页查询（1 个端点）
- **工作标准配置**: CRUD（5 个端点）
- **文件上传**: 通用上传（1 个端点）
- **仪表盘**: 统计数据（1 个端点）

### 前端交互组件

- **通知面板**: 右上角铃铛点击弹出，支持消息列表、标记已读、删除、全部已读、清空
- **用户面板**: 右上角用户名点击弹出，含头像、菜单项（消息中心/更换头像/个人设置/退出登录）
- **头像上传裁剪**: 两步流程（选择图片→拖拽裁剪预览→保存），使用 Canvas API 渲染裁剪结果
- **个人设置模态框**: 4 个分区（基本信息/通知偏好/显示设置/安全设置），数据持久化到 localStorage
- **角色切换**: 监理日记/日志/安全日志页面支持发起人/审核人视图切换
- **流程步骤指示器**: 监理通知单/工作联系单页面展示当前流程进度
- **工程资料目录树**: 旁站/日志/通知单/联系单/会议纪要/月报页面支持选择所属工程资料目录
- **版本历史面板**: 监理日记/日志/安全日志详情页展示多版本记录
- **点选式日期时间面板**: `assets/datetime-picker.js` 提供 date / hour / minute 三种模式（纯日期、日常巡检精确到小时、旁站精确到 5 分钟），面板内先预览、点“确定”才写回输入框并派发 change；取消、点遮罩、Esc 均不落值

## Testing Decisions

### 测试原则

- 仅测试外部行为，不测试实现细节
- 优先测试 API 层（Controller）作为最高测试接缝，验证 HTTP 请求/响应的完整性和正确性
- Service 层测试聚焦业务逻辑（状态流转、审核流程、回复机制、版本管理）
- 前端测试聚焦用户交互流程（表单提交、面板开关、数据填充）

### 测试接缝

| 接缝层级 | 测试内容 | 优先级 |
|---------|---------|--------|
| **API 端点（Controller）** | HTTP 请求/响应格式、状态码、分页参数、筛选条件 | 最高 |
| **Service 业务逻辑** | 状态流转（draft→pending→approved/rejected）、审核流程、回复机制、版本创建、唯一性校验 | 高 |
| **Repository 数据访问** | 动态查询条件构建、软删除过滤、树形结构查询 | 中 |
| **前端交互** | 表单提交、面板开关、从日记获取功能、头像裁剪 | 中 |

### 关键测试场景

1. **审核流程**: 日记提交→审核通过、日记提交→审核驳回→修改→重新提交→审核通过
2. **回复机制**: 通知单下发→回复→验证、联系单发送→回复→验证
3. **从日记获取**: 选择日期和项目→获取已审批日记→按作者分组填充→仅填充空字段
4. **版本管理**: 日记驳回→修改→新版本创建→版本历史查看
5. **权限控制**: 不同角色访问不同模块、无权限操作被拒绝
6. **分页与筛选**: 各模块分页查询、多条件组合筛选、边界值（空结果、超大页码）
7. **唯一性校验**: 项目编号、用户手机号、角色编码的唯一性约束
8. **软删除**: 删除后查询不返回、关联数据不受影响

### 现有测试基础

- 后端已有 4 个测试类（38 个测试用例通过），覆盖基础 CRUD 和部分业务逻辑

## Out of Scope

1. **移动端适配**: 当前仅考虑桌面端浏览器，不涉及移动端 App 或响应式移动布局
2. **实时通讯**: 不实现 WebSocket 实时推送，消息通过轮询或页面刷新获取
3. **电子签章**: 不集成电子签名或数字证书，审核操作通过账号权限控制
4. **第三方系统集成**: 不对接 OA、ERP、BIM 等外部系统
5. **离线功能**: 不支持离线使用，所有操作需联网
6. **数据导入**: 不支持从 Excel/Word 批量导入数据
7. **高级报表引擎**: 不集成 JasperReports 等报表引擎，报表以页面展示和简单导出为主
8. **多语言**: 不支持国际化，仅中文界面
9. **JWT/OAuth2 认证**: 当前使用简单 token 机制，不集成标准 OAuth2 或 JWT
10. **文件预览**: 不支持在线预览 PDF/Word/Excel 文件，仅提供下载
11. **消息推送**: 不支持短信/邮件/微信推送，仅系统内消息
12. **GIS/地图**: 不集成地图功能展示项目地理位置

## Further Notes

### 当前状态

- 前端 24 个 HTML 页面已完成 UI 开发，使用硬编码模拟数据
- 后端 Spring Boot 项目已完成 CRUD API 开发（约 80 个端点），数据库 schema 包含 16 张表
- 前端与后端尚未对接，需要逐页面替换模拟数据为真实 API 调用
- 后端认证机制为简单 token（`token-{userId}-{timestamp}`），密码明文存储，生产环境需升级为 JWT + BCrypt

### 已知技术债务

1. **认证安全**: 密码明文存储和比对，需改为 BCrypt 加密；token 机制需升级为 JWT
2. **前端数据层**: 所有页面使用硬编码模拟数据，需统一替换为 API 调用
3. **照片/附件存储**: 当前以 JSON 字符串存储在数据库 TEXT 字段，大量文件时可能影响性能
4. **跨域配置**: 当前允许所有来源，生产环境需限制为前端域名
5. **错误处理**: 前端缺少统一的 API 错误处理和全局异常提示
6. **无缓存层**: 未使用 Redis 等缓存，高频查询（仪表盘统计、权限树）可能成为瓶颈

### 部署信息

- 服务器：阿里云 ECS（推荐华东区域，2核4GB，CentOS/Ubuntu）
- 运行环境：JDK 17 + MySQL 8.0 + Nginx 1.20+
- 端口：Nginx 80（对外）、Spring Boot 8080（内网）、MySQL 3306（内网）
- 详见 DEPLOYMENT.md 部署文档
